# Event Journal

The Event Journal records important network events into a database file while Hive is running, so they can be analyzed after the fact (typically after an audio show where Hive was left running in the background). It is aimed at the sound engineer: only user-relevant events are recorded (entities going online/offline, stream connections, error counters, media clock lock, gPTP changes, ...), not internal debugging information (which belongs to the Logger window).

## Architecture

### Recording module

`hive::modelsLibrary::EventJournal` (in `libs/modelsLibrary`) is a singleton that listens to `ControllerManager` signals and normalizes them into journal events. It is UI-independent.

- A recording session automatically starts when the controller goes online (`controllerOnline` signal) and stops when it goes offline. Each session creates a new timestamped file in `<AppDataLocation>/EventJournals/` (eg. `~/Library/Application Support/KikiSoft/Hive/EventJournals/` on macOS).
- The oldest session files are automatically removed, keeping at most 50 files.
- The application attaches context metadata to the session (network interface) right after creating the controller.

### Storage: SQLite (via Qt Sql)

Events are persisted in an SQLite database (using the `QSQLITE` driver shipped with Qt, so no additional third party dependency).

Reasons for this choice (over a timeseries database like InfluxDB, or a flat JSON/CSV file):

- **Single self-contained file**: exporting is a file copy, importing is opening a file. No server to run.
- **Crash safety**: the database is written in WAL mode with `synchronous=NORMAL`; if Hive or the computer crashes during a show, all events written so far are recoverable (this is the primary use case of the feature).
- **Tooling**: journal files can also be inspected with any SQLite tool (`sqlite3`, DB Browser for SQLite, Python, ...) for advanced analysis.

File extension: `.hej` (Hive Event Journal). Writing details:

- While recording, the database is in WAL mode (crash-safe, low latency writes on the GUI thread, where all `ControllerManager` signals are emitted).
- On clean session stop, the file is converted back to `journal_mode=DELETE` so it becomes a single file (no `-wal`/`-shm` companions) that can be opened read-only from anywhere.
- Live export uses `VACUUM INTO`, which produces a consistent, self-contained snapshot without interrupting the recording.
- `EventJournal::loadSession()` opens files read-only, and falls back to read-write open (which performs WAL recovery) for sessions that were interrupted by a crash.

### Recording levels

Every event has a level, telling who it is for:

- `user` (default): what the sound engineer needs, the only level recorded unless diagnostic recording is enabled;
- `diagnostic`: everything needed for deep analysis and, later, for rebuilding the state of the network (much larger files).

Diagnostic recording is toggled from the Event Journal dock ("Record Diagnostic" button, not from the preferences), the choice is persisted (`settings::EventJournal_DiagnosticLevel`) so the next session starts in the same mode, and the current mode is shown in the dock status label. `EventJournal::setRecordingLevel()` applies it: user events are always written, diagnostic events only while the level is `Diagnostic`, and a switch during a session writes a user level `session` event (`Diagnostic recording enabled` / `Diagnostic recording disabled`) so any reader knows which periods carry diagnostic data (`metadata.recording_level_at_start` gives the initial mode). Enabling it also makes every monitored stream announce its `Stream data monitoring started` again at its next notification, so the diagnostic period starts with the coverage information.

Viewers hide the diagnostic events by default ("Show Diagnostic" button), so a diagnostic journal stays readable by a sound engineer; the Journal Analyser shows them by default.

### Schema (version 2)

```sql
CREATE TABLE metadata (key TEXT PRIMARY KEY NOT NULL, value TEXT);
CREATE TABLE entities (entity_id TEXT PRIMARY KEY NOT NULL, name TEXT);
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp INTEGER NOT NULL,          -- milliseconds since Unix epoch, UTC
    category TEXT NOT NULL,              -- session, entity, connection, counters, media_clock, gptp, link, latency, redundancy, streaming, configuration, control, marker
    severity TEXT NOT NULL,              -- info, warning, error, recovered
    entity_id TEXT,                      -- hex EID, empty for session-wide events
    entity_name TEXT,                    -- entity name at the time of the event (denormalized, so the file is self-contained)
    subject TEXT,                        -- sub-object designation (stream, interface, clock domain, ...)
    summary TEXT NOT NULL,               -- human readable description
    details TEXT,                        -- additional details, JSON object
    level TEXT NOT NULL DEFAULT 'user'   -- user, diagnostic (version 2)
);
CREATE TABLE snapshots (                 -- version 2, serialized entity models (see "Entity snapshots" below)
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp INTEGER NOT NULL,
    entity_id TEXT NOT NULL,
    reason TEXT NOT NULL,                -- online, session_start, cleared, manual
    format TEXT NOT NULL,                -- ave-msgpack-zlib
    data BLOB NOT NULL,                  -- the serialized entity, compressed
    uncompressed_size INTEGER NOT NULL
);
CREATE INDEX idx_events_timestamp ON events (timestamp);
CREATE INDEX idx_snapshots_entity ON snapshots (entity_id, timestamp);
```

Metadata keys: `schema_version`, `hive_version`, `hive_build`, `la_avdecc_version`, `os`, `computer_name`, `started_utc`, `stopped_utc` (written on clean stop only: a file without it was interrupted), `recording_level_at_start`, `snapshot_format`, `snapshots_count`, `snapshots_bytes`, `snapshots_serialization_ms` (size and cost figures of the snapshots, updated as they are written), `interface_id`, `interface_name`, and in dual-PI (redundant controller) mode `secondary_interface_id`, `secondary_interface_name`.

#### Compatibility rules

`metadata.schema_version` is the contract between writers and readers (`EventJournal::CurrentSchemaVersion`):

- schema changes are additive only: new tables, new columns with a default, new `details` keys, new `category` / `severity` / `level` values; a column is never renamed or dropped, the meaning of an existing value never changes, and an existing `summary` string is never changed (new information goes in `details`);
- a reader accepts any file whose version is lower than or equal to its own, and opens a higher version file in degraded mode rather than refusing it: the events are loaded, unknown `category` values fall back to `session`, unknown `severity` to `info`, unknown `level` to `user`, and the viewer shows a non blocking banner (`Session::isNewerThanReader()`);
- old files are never rewritten (no migration);
- every schema bump gets a row below and a fixture file of the previous version in `tests/data/eventJournal/` (`schema_v1.hej`, `schema_v2.hej`, ...), loaded by the `EventJournal_F.Session_*` unit tests.

### Entity snapshots

A journal is self-contained: the full entity model of every entity is stored in the `snapshots` table when the entity comes online (`reason = online`, right after its baselines are seeded, the row id is referenced by the `snapshot_id` details key of the `Entity is online` event), for the entities already online when a recording starts (`session_start`), and on demand ("Snapshot Now" button of the dock, diagnostic recording only, `manual`, journaled as a `Snapshot of N entities taken` session event). Clearing the journal (`Journal cleared`) wipes the snapshots too and snapshots every online entity again (`cleared`): the change tracking events written since the previous snapshots are gone with the clear, so the replay needs fresh anchors, and the entities that went offline before the clear must not resurface. Snapshots are written at both recording levels: they are what makes a journal usable without a network state dump.

Format `ave-msgpack-zlib` (`EventJournal::SnapshotFormat`): the la_avdecc JSON serializer output with the flags of a full entity export (ADP, compatibility, dynamic and static models, Milan, state, statistics, diagnostics) in the `.ave` binary encoding (MessagePack), compressed with `qCompress` (zlib). la_avdecc only serializes to files, so the writer goes through a temporary file in the system temporary directory. Measured on the field rig dump (77 entities loaded in a virtual controller, release build): 5.84 MB serialized, 410 KB stored (max 9 KB per entity), 103 ms of total serialization time on the GUI thread (1.3 ms per entity), so no worker thread is needed. `EventJournal::loadSnapshotsIndex()` reads the index without the blobs and `loadSnapshotData()` returns one decompressed entity, ready for `ControllerManager::loadVirtualEntityFromJson()` with the `BinaryFormat` flag (through a temporary file again).

The `Entity is online` event carries, in its `details`, the static description the analysis scripts need without decoding the snapshot: `entity_model_id`, `vendor` (OUI database), `firmware_version`, `milan_version` (Milan entities only), `avb_interfaces` (array of `{index, mac, clock_identity, grandmaster_id, priority1, as_path, propagation_delay}`, so the rack and branch of every plane is in the journal), `clock_domains` (array of `{index, clock_source_index, clock_source_stream_index}`, the last one only when the clock source is an input stream), `stream_inputs` (connected streams only, `{index, name, avb_interface_index, talker_entity_id, talker_stream_index}`, the interface being the network plane of the stream), `is_controller` (the entity implements a controller: the other controllers of the network are identified from these events), `snapshot_id` and `enumeration_time_ms`.

The gPTP AsPath of an interface is journaled on change (`gPTP AsPath changed`, category `gptp`, severity `info`, user level, `details.previous_as_path` / `new_as_path`): a topology event. The propagation delay of a link jitters by a few nanoseconds between measurements (5 to 16 ns on the field rig), so its changes are journaled at diagnostic level only (`gPTP propagation delay changed`, `details.previous_propagation_delay` / `new_propagation_delay`).

### Change tracking events and the JSON patches

At diagnostic level, every dynamic model change the controller notifies is journaled with a human readable summary and, in `details.patch` (`EventJournal::PatchDetailsKey`), a JSON Patch (RFC 6902) applying the change to the AVE document of the entity (the format of the snapshots): the state of an entity at any time of the session is its last snapshot plus the patches of the events journaled since (one generic loop, see "Replay engine" below). The patch rules:

- only `replace` operations, because the la_avdecc serializer always writes the targeted keys (an unset optional is written as `null`), so an operation applies whatever the previous value;
- the paths are JSON Pointers (RFC 6901) rooted at the snapshot document, built by `libs/modelsLibrary/avePatch.hpp` from the descriptor type and index: the serializer writes the descriptors of a configuration as arrays ordered by index, and the nested descriptors (controls of an audio unit, jack, stream port or PTP instance; stream ports of an audio unit; audio clusters and audio maps of a stream port; PTP ports of a PTP instance) under their parent at the position "index minus the base index of the parent", looked up in the entity model (eg. `/entity_model/entity_descriptor/configuration_descriptors/0/audio_unit_descriptors/0/stream_port_output_descriptors/0/audio_cluster_descriptors/1/dynamic/object_name` for audio cluster 9 when the output stream port starts at cluster 8);
- the values are serialized by la_avdecc itself (`la/avdecc/internals/jsonTypes.hpp`), so they match the snapshots byte for byte; the acquire and lock states and the compatibility flags, serialized by the controller's private serializer, use the same names, rebuilt in `eventJournal.cpp`;
- an event without `patch` is a change the replay cannot apply (the talker side connections, not stored in the AVE document, or a descriptor that could not be located); a patch targeting a descriptor of a non active configuration (only its names can change) does not apply either, because the serializer only writes the dynamic model of the active configuration: the replay must count the operations it could not apply and say so;
- every change is deduplicated by value against the last journaled value of the item (baselines seeded from the entity model when the entity comes online): a redundant controller receives every notification once per interface, and la_avdecc does not compare the values of every notification before notifying.

**Raw counters.** A counters notification is journaled once per descriptor and notification, with the counters that changed since the last journaled set and a patch of the whole set, except when nothing changed (a duplicate notification, or a notification triggered by a counter Hive does not display) and when only the liveness counters moved (`FRAMES_RX`, `FRAMES_TX`, `TIMESTAMP_VALID`, `LivenessCounterNames`): on the field rig every connected stream produces one such notification per second (about 300 per second in total), which would flood the journal for nothing, the `FRAMES_RX` increments being consumed by the stream data loss rule instead. Four devices of the rig also expose `FRAMES_RX` / `FRAMES_TX` in their AVB interface counters, hence the rule applies to every descriptor type. The liveness counters are still part of the tracked set, so the first informative change after a long streaming period reports their previous values correctly. The user level events derived from the counters (error counters, media clock transitions) are unchanged and written at both levels. No time based coalescing is done (the plan suggested 100 ms per entity): the value dedup and the liveness exception remove the identified sources of floods, the actual volume is to be measured on the first diagnostic session of the rig.

**Control values rate limiting.** Faders and meters can notify several times per second: a control journals at most one value change per second (`ControlValuesRateLimitInterval`). The first change is journaled at once; the following changes within the interval are kept pending (the last value wins, the same value again is not a change) and journaled by a single shot timer once the interval elapsed, with `details.coalesced` counting the changes that were skipped (the summary says `(N changes coalesced)`). The pending values are flushed when the session stops, so no value is lost, only intermediate ones. The values are serialized like the AVE document (`{"type": "CONTROL_LINEAR_UINT8", "values": [10]}`).

### Replay engine

`hive::modelsLibrary::JournalReplay` (in `libs/modelsLibrary`, UI independent, unit tested) rebuilds the AVE document of every entity as it was at any event of a loaded session, from the snapshots index and the events (the snapshot blobs are loaded on demand through a caller supplied function, `EventJournal::loadSnapshotData` bound to the file). The cursor is an event index (`seekToEvent`, or `seekToTimestamp` for the last event at or before an instant): the state includes the selected event, so two events in the same millisecond are told apart. The rules:

- the anchor of an entity is its last snapshot describing it at the cursor: the snapshot with the greatest timestamp at or before the event's, the `session_start` and `cleared` snapshots being taken as valid from the first event of the session (they are written a few milliseconds after `Recording started` or `Journal cleared`, and the network was already there);
- the entity is absent when it has no anchor, when an `Entity went offline` event of its own or a `Controller stopped` session event (the controller stopping does not journal the entities offline one by one) was journaled at or after the anchor and at or before the cursor (an entity coming back gets a new snapshot, which becomes the anchor), or when its snapshot cannot be loaded;
- otherwise its document is the anchor plus the patches of its events journaled at or after the anchor and at or before the cursor, in journal order (`nlohmann::json::patch_inplace`); the events written before the snapshot in the same millisecond replace values the snapshot already holds, harmlessly. A patch that does not apply (the name of a descriptor of a non active configuration, see above) is counted as rejected and leaves the document as it was, so the caller can show the fidelity (`EntityState::appliedPatches` / `rejectedPatches`, plus the anchor's id, timestamp and reason);
- the documents are cached per entity: moving the cursor forward from the same anchor applies only the patches in between, moving it backward rebuilds only the entities with a snapshot or a relevant event between the two positions, and the other entities are untouched. Every seek returns the entities whose document changed and the entities that disappeared (`Changes`), so a consumer only reloads what moved.

Measured in the analyser on the field rig journal (77 entities, release build): the initial seek at the end of the session decodes the 77 snapshots and loads them in the virtual controller in 463 ms (6 ms per entity, snapshot read and decompression, MessagePack decoding, temporary file and virtual controller included), unloading the 77 entities when the cursor passes `Controller stopped` takes 47 ms, and a step between two events of the same anchor takes a few milliseconds per entity that changed.

All the events of this table are `user` level, except `Stream data monitoring started`, `gPTP propagation delay changed`, the `Media locked` information of a stream (the one closing no journaled unlock), the informational counter events, `Heartbeat`, `AECP response time changed` and the change tracking events other than the operator changes listed above (`diagnostic`).

The `Recovered` severity marks the end of a previously reported error condition, so the duration of an incident (clock unlock, link down, ...) is directly visible in the journal.

To only record actual changes (and not the initial state of each entity being enumerated), the module seeds change-detection baselines from the entity model when an entity comes online (`EventJournal::Private::seedBaselines`), and error counters are compared against their previously recorded values (the values Hive displays, since the last acknowledgement: they restart from zero when the entity is enumerated and when the user acknowledges them, the latter being journaled).

### Notification origin

Every event journaled while a notification of la_avdecc is being delivered carries in its `details` the origin of that notification: `origin` is `unsolicited` (an unsolicited notification sent by the entity), `response` (the response to a command of the controller: an enumeration, a refresh or a command of the application) or `sniffed` (an ACMP response to the command of another controller, observed on the network), and `interface` is `Primary` or `Secondary` (the interface the message was received on, always `Primary` outside of the redundant mode). This covers the change tracking events, the raw counter events and the events derived from the counters (media clock and stream locks, link, gPTP grandmaster counter, stream data loss, error counters), the connections, the gPTP changes, the acquire and lock changes, the compatibility and capabilities changes, the unsolicited notifications subscription events (a registration response, or the notification whose sequence gap revealed a loss): an event without `origin` was not carried by a message (a virtual entity being modified, a session or marker event, the heartbeat, the controller interface events, the statistics of the controller). A counter event with `origin: response` is a value the controller polled (at the entity online, after a refresh) rather than a change the device pushed, and in redundant mode the same change reaches the journal once per interface, `interface` telling them apart (the rules deduplicating by value make the second one silent, see "Counter semantics").

The plumbing: la_avdecc sets the context of the message it dispatches on the thread of the protocol interface (`entity::controller::DispatchContext`, `ControllerEntity::getCurrentDispatchContext()`), the controller maps it to `Controller::getCurrentNotificationOrigin()` (the `ControllerEntity` that received the message identifies the interface), `ControllerManager` reads it in the observer callback and emits its signal on the main thread with the origin exposed through `ControllerManager::currentNotificationOrigin()` for the duration of the emission, and `EventJournal::addEvent()` adds the keys. The `interface` key is not overwritten when an event already tells its interface (the statistics events).

### Counter semantics

Counters are classified in three groups. Only the first group produces `error` severity events, the rest is information, never shown as an error:

- **errors** (the counters Hive flags in the UI): stream input `Stream Interrupted`, `Sequence Number Mismatch`, `Late Timestamp`, `Early Timestamp`, `Unsupported Format` and the controller statistics (`'<Name>' error counter increased to N`, `details.counter`, `previous_value`, `value`: the values Hive displays, since the last acknowledgement), plus the state transitions derived from the counter pairs below (`Media clock unlocked`, `Media unlocked`, `Link down`), closed by their `recovered` counterpart (`Media clock locked`, `Media locked`, `Link up`);
- **informational**: stream input `Media Reset`, `Timestamp Uncertain`; stream output `Stream Start`, `Stream Stop`, `Media Reset`, `Timestamp Uncertain` (`'<Name>' counter increased to N`, severity `info`, diagnostic level, `details.counter`, `previous_value`, `value`, `increment`, absolute values; a readable line next to the `Counters updated` event, which carries the same change in `details.changed`); AVB interface `GPTP_GM_CHANGED` (`'GPTP GM Changed' counter increased to N`, user level, see below); everything else (`Rx CRC error`, `Timestamp Valid` / `Not Valid`, the entity counters, ...) is only visible in the `Counters updated` events;
- **liveness**: `FRAMES_RX`, `FRAMES_TX`, `TIMESTAMP_VALID`, never journaled per increment (the `FRAMES_RX` increments feed the stream data loss rule below).

#### Transitions inferred from the counter pairs

Three states are derived from a pair of counters counting the entries into and the exits from the state (`EventJournal::Private::replayCounterPairTransitions`): the media clock lock of a clock domain (`LOCKED` / `UNLOCKED`, locked when `LOCKED > UNLOCKED`, same rule as the Discovered Entities list), the media clock lock of a stream input (`MEDIA_LOCKED` / `MEDIA_UNLOCKED`, same rule) and the link of an AVB interface (`LINK_UP` / `LINK_DOWN`, up when `LINK_UP == LINK_DOWN + 1`, the rule la_avdecc derives its link status from, Milan 1.3 Clause 5.3.6.3). The counters are only notified once in a while: a clock that unlocks and relocks (or a link that goes down and comes back) between two notifications increments both counters without changing the derived state. Rather than losing those events, the journal replays the transitions implied by the counter increments since the previous notification, in the only order consistent with an alternating sequence starting from the previous state, and always ends on the state derived from the counters. Every event carries the raw values in `details` (`locked_counter`, `unlocked_counter`, `locked_increment`, `unlocked_increment` for the clock domains; `media_locked_*` / `media_unlocked_*` for the streams; `link_up_*` / `link_down_*` for the links), and the transitions that could not have been observed by comparing the states before and after the notification carry `"inferred": true` (all of them when the state did not change, all but the last one otherwise). Inferred events share the timestamp of the notification, so the duration of an inferred unlock or flap is not known (only that it was shorter than the notification interval). A counter going backwards (device reboot, counters reset) carries no usable increment: only the resulting state is compared. The first notification of a descriptor without a baseline (entity without counters at enumeration time) only seeds the baseline.

Per notification rules like these are immune to the duplicate notifications a redundant controller receives (one per interface): the same counters again produce no increment and no state change.

**Clock domains** (`Media clock unlocked` / `Media clock locked`, category `media_clock`, subject `Clock Domain N`): the details also name the clock source the domain follows at the time of the event, `clock_source_index`, `clock_source_type` (`INTERNAL`, `INPUT_STREAM`, `EXTERNAL`, `EXPANSION`) and, when the source is an input stream, `clock_source_stream_index`, `clock_source_talker_id` and `clock_source_talker_stream_index` (the stream connection at the time of the event), so the analysis can tell which stream a system wide unlock started from.

**Stream inputs** (`Media unlocked` / `Media locked`, category `counters`, subject = the input stream, `details.talker_id` / `talker_stream_index` when connected): only a connected stream is expected to be locked (the connection state is read live from the entity model, the same source as the `Media Unlocked` error counter of the UI and the stream data loss rule), so the unlock of a stream being disconnected is dropped, and `Media unlocked` is an `error` closed by the `Media locked` recovery of the same stream. A lock closing no journaled unlock (the stream was just connected, or its talker just started streaming) is not a recovery: it is journaled as `info` at diagnostic level. For the streams exposing both counters, these events replace the `'Media Unlocked' error counter increased to N` event (which stays for a stream exposing `MEDIA_UNLOCKED` alone): every unlock the device counted is in the journal, with its relock, so the unlock durations of every plane can be measured and the periods where both copies of a redundant stream were unusable at the same time can be found.

**Links** (`Link down` / `Link up`, category `link`, subject `AVB Interface N`): the journal tracks the counters directly rather than the link status la_avdecc derives from them, so a link that went down and came back between two notifications is journaled as an inferred `Link down` / `Link up` pair instead of being lost.

**gPTP grandmaster changes** (`'GPTP GM Changed' counter increased to N`, category `gptp`, severity `info`, user level, subject `AVB Interface N`): every increase of the counter is journaled with `details.previous_value`, `value`, `increment`, `previous_grandmaster_id` (the grandmaster known at the previous counters notification) and `grandmaster_id` (the one known now). A grandmaster change the controller observed is already journaled from the AVB interface information (`gPTP grandmaster changed to X`, severity `warning`); an increase while the grandmaster is the same before and after (an even increment, typically) means the grandmaster changed and came back between two notifications. The counters and the AVB interface information are notified separately, in no defined order, so the journal states the facts and leaves the flip and back conclusion to the analysis (the summary never claims it).

### Markers, heartbeat and controller side context

**Markers** (`EventJournal::addMarker()`, category `marker`, severity `info`, user level): what the user heard or did, so it lines up with the events of the journal. The summary is the text, `details.author` the computer name of the session. The Mark button of the journal dock offers a custom text and the quick markers `Show start`, `Show end`, `Glitch heard`, `Network work start`, `Network work end`; the Tools menu action (`Ctrl+Shift+M`) asks for a custom text whatever the visibility of the dock. The timeline draws every marker as a labeled tick across every lane, and the CSV export carries them like any event.

**Heartbeat** (category `session`, summary `Heartbeat`, diagnostic level, every five minutes, `HeartbeatInterval`): proves the controller was alive during the silences of a journal and tells how loaded it was. `details`: `entities_online`, `events_since_last` (events written since the previous heartbeat, at both levels), `notifications_since_last` (unsolicited notifications received from the online entities since the previous heartbeat, AEM and MVU on every controller interface, from the controller statistics), `event_loop_latency_ms` (the event is written by a zero timer scheduled when the period elapses, so the delay before it runs is the time the main thread needed to drain the notifications queued before it) and `process_rss_mb` (resident memory of the process). The counters are restarted at every period even at user level, so a switch to diagnostic recording starts with a meaningful period. A file whose last event is neither `Recording stopped` nor preceded by a recent heartbeat was interrupted (`Recording stopped` and the `stopped_utc` metadata are written on clean stop only, at user level).

**Controller interfaces** (category `link`, user level, subject `Primary Interface` / `Secondary Interface`, `details.interface_id`, `interface_name`): the journal observes the network interfaces of the computer (`la::networkInterface::NetworkInterfaceHelper`, notifications forwarded to the main thread) and journals the ones the controller runs on (the `interface_id` and `secondary_interface_id` session metadata): `Controller interface link down` (`error`) / `Controller interface link up` (`recovered`) on the connected state, `Controller interface disabled` (`warning`) / `enabled` (`info`) on the enabled state, `Controller interface removed` (`warning`). A link down on the controller computer explains the entities going offline right after. The link speed is not available from the helper.

**AECP response time** (category `entity`, summary `AECP response time changed to N ms`, diagnostic level, subject `Primary Interface` / `Secondary Interface`, `details.interface`, `previous_average_ms`, `average_ms`): the average response time of an entity to the controller's AECP commands, per controller interface (`aecpResponseAverageTimeChanged`), journaled when it moved by at least 50 ms (`AecpResponseTimeChangeThreshold`) since the last journaled value (seeded from the entity when it comes online). A few milliseconds on a healthy network, so a jump tells the device or the network was struggling.

### Stream data loss detected from the `FRAMES_RX` increments

An input stream that stops receiving data is only reported by the device itself through the `STREAM_INTERRUPTED` counter, whose trigger is implementation defined (the field journals show thousands of `Media Unlocked` events for a handful of `Stream Interrupted`). The journal therefore also watches the data reception from the controller side, using what Milan 1.2 guarantees:

- `FRAMES_RX` is mandatory on every Stream Input (table 5.16) and is "incremented at the end of every observation interval during which at least one Stream Data AVTPDU has been received", the observation interval being implementation specific and at most one second (table 5.6);
- a device sends at most one `GET_COUNTERS` unsolicited notification per descriptor per second (table 5.22), so two consecutive notifications of a stream are at least one second apart and, while frames flow, the increment between them is at least one second worth of frames;
- the Stream Input counters are reset each time the stream goes from not bound to bound.

**The rule** (`EventJournal::Private::handleStreamInputCountersChanged`, no timer): for every stream input that is connected (state read live from the entity model at evaluation time, the same source as the `Media Unlocked` rule) and carries `FRAMES_RX`, the increment `d` between two consecutive notifications is computed modulo 2^32 (the counter wraps every few days at 8000 frames per second) together with the time elapsed between their arrivals on the main thread. The expected one second worth of frames `e` is learned per stream as the 10th percentile of the last 30 increments (the low end is the reference: a device whose cadence varies between one and two seconds produces larger increments, and a single undetected partial loss must not lower the reference); nothing is evaluated before 10 increments. Then:

- `d = 0` is not a new observation: a redundant (dual interface) controller receives every notification once per interface, with the same payload a few ms apart (or seconds apart when the main thread stalled between the two), and a notification triggered by another counter while no frame arrived tells nothing the next one will not tell with a longer elapsed time. It is ignored entirely (the reference sample is not moved);
- a notification arriving less than 900 ms after the previous one (queued burst after a main thread stall, the other interface of a redundant controller having re-read the counter a few frames later, non compliant device) only moves the reference sample: it is neither evaluated nor learned, so it can neither raise an event nor lower the reference;
- `d > 10 x e` is a counter reset (rebind) or a value jump: the reference sample is resynchronized, nothing is journaled, the learned increments are kept;
- `d < 0.5 x e`: one `Stream data loss: about N ms of frames missing` event (category `streaming`, severity `error`, subject = the input stream), with `details.frames_rx`, `increment`, `expected_increment`, `elapsed_ms`, `missing_ms` (`(e - d) / e x 1000`, the estimate assumes a one second device cadence), `talker_id` and `talker_stream_index` (so listener and talker events can be joined without a network state dump). The alerted increment is not learned, so repeated partial losses keep being reported against the same reference.

The learning restarts when the connection of the stream changes (the counters are reset by a rebind and the first increment after a connection is partial) and when its stream format changes (the frame rate may change). The baseline of a connected stream is seeded from the entity model when the entity comes online. The end of the learning phase is journaled once per stream as `Stream data monitoring started` (severity `info`, level `diagnostic`, so only with diagnostic recording enabled; `details.expected_increment`, `samples`, `talker_id`, `talker_stream_index`): a stream without that event is not monitored (no `FRAMES_RX`, not connected, no frames received so far, or a device counting once per observation interval of one second, for which `e = 1` and the threshold is never crossed).

**Why it produces no false positive** (the guarantee the journal must keep): every controller side problem makes the increment larger or delays it, never smaller. A lost unsolicited notification doubles the next increment; an expired subscription or a controller interface down stops the notifications, then delivers a large increment; a stalled main thread delivers the queued notifications in a burst with normal increments and no elapsed time (not evaluated); a counter reset or a wrap goes through the modular arithmetic and the `10 x e` rule; a stream the user just disconnected is already seen as not connected when its last partial second is processed (la_avdecc updates its model before the queued notification reaches the main thread). Only a stream that really received less than half a second worth of frames in an interval of at least 900 ms is reported, which includes a talker deliberately stopped (`STOP_STREAMING`) or gone offline: a true positive, explained by the other events. In exchange the rule only sees an interruption at its edges: a long silence gives an event at its start (when the cut falls in the first half of the device interval), nothing during the silence (the device has nothing to report) and an event at the resume, whose `elapsed_ms` is the duration of the silence. Events of the two members of a redundant stream within the same second are the "both planes" signal; they are correlated at analysis time, not at recording time.

Known residual exposure, to be checked during the field validation: a redundant controller whose devices re-read the counter for the second interface (a near duplicate, a few frames above the first one) combined with a main thread stall starting between the processing of the two copies would evaluate the near duplicate as a tiny increment over a long interval. Such a false event is recognizable (`increment` of a few frames, `elapsed_ms` equal to the stall, one stream at a time); if it shows up, the fix is to ignore increments below a few frames, not to add a watchdog.

Deliberately not done: a timer based watchdog on the absence of notifications (it cannot distinguish a device receiving no frames from a controller receiving no notifications and would reintroduce controller side false positives), `recovered` events, redundant pair state at recording time. The only tuning knob is the loss threshold (`StreamDataLossThreshold`, 0.5): the noise floor of the increments is a few percent, so it can be lowered after a field validation if the edge events turn out to be too rare.

## Viewer UI

`EventJournalView` (in `src/eventJournal/`) displays a session with filtering, in two modes (same pattern as the Entity Model Inspector):

- **Live**: embedded in the `MainWindow` "Event Journal" dock (View menu, hidden by default), following the current recording session, with auto-scroll, an Export button and a Mark button (custom marker or quick markers, see "Markers, heartbeat and controller side context" above; `Tools > Add Event Journal Marker...`, `Ctrl+Shift+M`, works whatever the visibility of the dock).
- **File**: `File > Open Event Journal...` opens any journal file in a standalone viewer window (multiple windows can be opened, eg. to compare with the live session).

Features: severity/category/entity filter menus, diagnostic level events toggle, free text search (regular expression), time range filter, per-severity row colors (error/warning/recovered), details pane for the selected event, event counters, degraded mode banner for files written by a newer schema. `EventJournalModel` + `EventJournalFilterProxyModel` (in the same directory) implement the table and filtering.

A timeline strip (`EventJournalTimeline`) is displayed above the table, plotting the filtered events on a time axis with one lane per category, so recurring problems (eg. repeated gPTP grandmaster changes) and their spacing in time are directly visible. Markers are colored by severity; mouse wheel zooms around the cursor, left drag pans, double-click fits the whole session, hovering a marker shows its details (including the time elapsed since the previous event of the same category), and clicking a marker selects the event in the table (selection is synchronized both ways). The markers written by the user are also drawn as labeled ticks across every lane, and the time cursor of the analyser (the instant its twin of the network shows) as a solid line.

`File > Export > Event Journal...` exports a snapshot of the current session at any time while recording.

The Export button of the viewer offers two formats: a journal file snapshot (live session only) and a CSV file (all events or only the currently filtered ones, with a Level column), for analysis in a spreadsheet.

### Analysis engine

`hive::modelsLibrary::JournalAnalysis` (in `libs/modelsLibrary`, UI independent, unit tested) computes from a loaded session the figures the after show reports used to need scripts for, and renders them as a Markdown report with the structure of the hand written `*_Analysis.md` reports (`markdownReport`, with the times as `event:<index>` links for the analyser's Findings pane, or plain for the exported file). The interpretation and the recommendations stay the analyst's: the report is the fact base, computed the same way for every journal.

The topology comes first (`JournalAnalysis::Topology`): the rack and branch of every entity on every plane from the gPTP AsPath of its interfaces (the last hop before the entity is its rack switch, the one before is its branch switch; an entity plugged directly into a switch serving other racks is a rack of its own on that switch, so a device on a branch switch port joins the sweeps of that switch), and the plane of every input stream from the interface it is attached to. It is built from the `Entity is online` details of a schema version 2 journal (followed by the `gPTP AsPath changed` and `Connected to talker` events), completed or, for a schema version 1 journal, replaced by the AVE documents of a network state or virtual entity file (`addNetworkState` / `addEntityDocument`, the same MessagePack format as the snapshots). Without an AsPath, the stream events are still attributed to a plane from the naming of the stream (`Primary` / `Secondary`), and only the rack and branch figures are missing.

The computations, each with the thresholds of `JournalAnalysis::Options` (the defaults are the rules of the hand written reports, and the report states them in its last section):

- **session shape**: entities online at the start and in the whole session, other controllers seen, waves of entities going online or offline together (power ups and power downs), drop outs (an entity offline then back, the ones preceded by an `Entity refresh requested` told apart), heartbeat continuity (median interval, gaps of more than twice the interval, event loop latency outliers), controller interface events, markers, whether the session was interrupted (last event not `Recording stopped`);
- **event breakdown** by category and severity and by summary family (numbers and names stripped), and the absent categories;
- **media clock unlocks at stream level** (the timing family: `Media unlocked` events, or the `'Media Unlocked' error counter increased` events of older journals) aggregated at increasing scale: hits (same entity and plane within 1 s), rack incidents (the entities of a rack switch on a plane within 1 s, with whether the whole rack was involved), storms (incidents of a rack and plane less than 60 s apart), runs (storms of a branch and plane less than 30 min apart, the racks in order of their main storm), and run series per branch and plane (the sweeps visiting several racks, their periodicity and whether the port order repeats: a fixed non numeric order and a stable period are the signature of a scheduled process in the switch);
- **system wide events**: entities touched (stream level or clock domain unlock) within 2 s of each other, at least 25 % of the entities reporting hits in the session (4 at least) across several rack switches, extended by the hits of the same entities within 15 s of the end (the relock wave); per event the planes, the entities hit, the rack and branch switches, how completely each branch was hit and the entities spared (what localizes the origin above the racks), the clock domain unlocks with their durations, and the accompanying grandmaster, link, packet loss and stream data loss events. Their incidents are excluded from the storms and runs (the background);
- **rankings**: per rack and plane (incidents, background incidents, members), per branch and plane, per entity (hits per plane and clock domain unlocks, median, minimum, maximum);
- **both planes**: primary and secondary hits of the same entity paired within 5 s (greedy, each hit used once), with the delay distribution, the simultaneous pairs (below 100 ms, a common source) and the background pairs outside of the system wide events; with the `Media unlocked` / `Media locked` pairs, the periods where a primary and a secondary stream of the same entity were unlocked at the same time (the audible ones);
- **durations**: `Media clock unlocked` / `locked`, `Media unlocked` / `locked` and `Link down` / `up` pairs per entity and subject (inferred pairs and pairs never closed have no duration), with the distribution, the longest clock domain unlocks, what accompanied each clock domain unlock at stream level (primary only, secondary only, both, none) and the share of stream hits accompanied by a clock domain unlock, and the entities unlocking their clock domain at two or more system wide events (a per device property when the same subset unlocks every time);
- **other families**: grandmaster change storms (changes less than 10 s apart, with the planes, entities, flips and the accompanying packet loss and clock domain unlocks), `'GPTP GM Changed'` counter increases and AsPath changes, link intervals, packet loss counters per counter, entity, stream and plane, controller side counters per counter and interface, redundancy events per interface, latency errors, connection changes and the operator actions (control events and user level configuration changes);
- **stream data losses**: the covered streams (`Stream data monitoring started`) with their learned references per plane, the connected streams not covered (from the topology, only when the journal has the monitoring events), losses per stream and plane with the `missing_ms` histogram, both planes of the same entity within the same second, the losses accompanied by a media unlock of the same stream, the long interruptions (elapsed time over 3 s) paired with their start edge, and the incidents (the listeners of one talker stream hit within 1 s) with the deepest switch common to the AsPath of the listeners hit and the listeners of the talker behind that switch that were spared.

Checked against the two hand written reports of the touring rig: the figures match (hits, incidents, both planes pairs and delays, the five system wide events of the 6 h 46 journal with their clock domain unlocks, the runs of the 45 h journal with the same port orders and periods per switch), and the analysis of the 14 000 events journal takes about 30 ms.

## Journal Analyser

`JournalAnalyser` (in `tools/JournalAnalyser/`) is a standalone application dedicated to the offline analysis of journal files, so a show can be analyzed without running Hive (and without a network interface). It links the `Hive_static` library to reuse the Hive widgets as they are:

- the journal viewer (`EventJournalView` in file mode, with its filters, search and timeline) as central widget;
- standalone `EntityInspector` windows, opened by double-clicking an event (one window per entity, raised when already open);
- the `NetworkGraphView` in a dock widget;
- the **Findings** dock: the report of the analysis engine (see "Analysis engine" above), rendered from Markdown, computed when the journal is loaded and again when a network state or virtual entity file completes the topology (the `.ans` and `.ave` files are also read by the analysis, which needs their AsPath and connections for a schema version 1 journal). The times of the report are links: clicking one selects the event in the journal (the twin follows it when following the selection), or tells in the status bar that the event is hidden by the current filters. `File > Export Report` writes the same report (plain times) as a Markdown file next to the journal (`<journal>_Report.md`), the fact base of the analysis workflow of `EventJournalAnalysisPrompt.md`.

The entities are hosted by a **virtual controller** (`ProtocolInterface::Type::Virtual`, no network access) holding the **twin of the network**: the entities as they were at the time cursor, rebuilt by the replay engine (see "Replay engine" above) from the snapshots and the change tracking events of the journal. The Replay toolbar drives the cursor: with **Follow Selection** (checked by default) the twin follows the selected event, so stepping through the events with the keyboard shows the network evolving in the graph and the inspectors; unchecked, only a double-click moves the twin, and a double-click always brings the twin to that event before opening the Entity Inspector of the entity (which therefore shows the entity as it was then). **Latest** jumps to the last event. The toolbar label tells where the twin is (`Twin at <time> (event N of M): E entities online, P patches applied, R rejected (X ms)`) and the timeline draws the cursor as a solid line. When a journal is opened, the twin starts at the last event that is not a session event (a session normally ends with `Controller stopped`, after which nobody is online), so the inspector and the graph show the network as last seen during the session. The entities are loaded in the virtual controller through a temporary `.ave` file each (la_avdecc only loads files), only the entities whose document changed are reloaded when the cursor moves, and the `NetworkTopologyModel` recomputes the graph from the controller as they come and go. A journal at user level only replays the user level changes (names, formats, connections, gPTP, acquire and lock), which the patch figures make visible.

A network state file (`File > Load Network State`, or `.ans`/`.ave` files given on the command line or dropped on the window) replaces the twin, as an explicit override (the toolbar says so and the cursor stops following), and is the only source for journals predating the snapshots (schema version 1). Double-clicking an event whose entity is not loaded shows a hint in the status bar (offline at the time of the twin, or no snapshot of it).

The application runs **one instance per journal**: journal files are given as positional command line arguments, and a journal opened while one is already loaded (File > Open, drag and drop, or a macOS FileOpen event, which Launch Services always routes to the running instance) is started in a new process (`QProcess::startDetached` on the application executable). The analyser keeps its own settings file (`KikiSoft/JournalAnalyser.ini`, same location scheme as Hive) for the theme color, appearance and graph layout, so Hive's preferences are never touched.

## File association

The `.hej` extension is associated with the Journal Analyser on macOS (`JournalAnalyser.plist.in` document type, `Owner` rank, Hive no longer declares it) and on Windows (installer file association pointing to `bin/JournalAnalyser.exe`, whose first icon is `Icon_HEJ.ico`), so double-clicking a journal file opens it in the analyser, in a new instance. On Linux the AppImage only bundles Hive, so the `application/x-hive-hej` mime type keeps opening journals in Hive until the analyser gets its own package.

Hive itself still opens journal files through `File > Open Event Journal` (standalone viewer window in the running Hive): `MainWindowImpl::loadFile()` handles the extension like `.ave`/`.ans` files (command line arguments, macOS FileOpen events, and forwarding to the already running instance on Windows). On macOS, FileOpen events received before the MainWindow is created (eg. while the splashscreen is displayed) are buffered by `HiveApplication` and loaded once the window exists.
